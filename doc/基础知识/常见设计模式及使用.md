# 常见设计模式及使用

本篇只写这套后端里会碰到的三种写法。名称用来对照代码，不展开其他模式。前端对应的三种是依赖注入、仓储和观察者。这里没有页面订阅，第三种是守卫。

## 目录

- [依赖注入](#依赖注入)
- [仓储](#仓储)
- [守卫](#守卫)

## 依赖注入

调用方不创建依赖，模块按构造函数传入。`SecurityApplication` 需要用户仓储、口令和凭证时，只声明参数类型，不写 `new PrismaUserRepository()`。

模块写法见 [DI是什么](./DI是什么.md)。

## 仓储

仓储把「业务要的数据」和「数据放在哪」分开。

`IUserRepository.findByUsername` 返回 `UserEntity` 或 `null`。用例只调用这个方法，再决定签发凭证还是抛出 401。`PrismaUserRepository` 才知道表名和 `roles` 存在一个 JSON 字符串里。

`IProjectRepository` 声明 `list`、`get`、`save`。`PrismaProjectRepository` 把 `Document` 存成 JSON 字符串，读出时用 `projectFromRecord` 收成 `Project`。

因此 `domain` 不出现 Prisma，`infra` 不决定登录成功后要返回哪些公开字段。

## 守卫

请求进入用例之前，先回答这次调用者是谁。`JwtAuthGuard.canActivate` 做这件事。

标了 `@Public()` 的路由跳过凭证。其余路由从 `Authorization` 取出凭证，核对后再把 `Actor` 放到 `request.user`。`CurrentUser` 把这个 `Actor` 交给控制器参数。

用例方法接收 `Actor`，不解析请求头。项目能不能被这个调用者打开，仍由 `Project.assertAccessible` 决定。
